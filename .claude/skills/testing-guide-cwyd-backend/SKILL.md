# Testing guide — cwyd-backend

## 0. Purpose

This guide helps you decide **what to test**, at **which layer** and **how to set up tests**
for each artifact type in `backend/`: settings, routes, Postgres adapters, the composition
root, domain models, use cases, LLM/embedding adapters and the types that arrive later
(parsers, exception handlers, indexing jobs, streaming). When working on one type, read its
file in `artifacts/`. Mock strategies, file conventions and gotchas are in `references/`.

## 1. Testability Foundations

- **Ports and adapters decide the mock boundary.** Use cases depend on `typing.Protocol` ports
  (`ChatModelPort`, `EmbeddingPort`, `DocumentRepository`, `RetrieverPort`…). A use-case unit
  test passes declared fakes that implement those ports; the adapter behind each port gets its
  own integration test. Neither replaces the other: the fake proves the use case's logic, the
  integration test proves the SQL or provider mapping.
- **The database is a contract, not a detail.** Retrieval quality depends on real pgvector
  operators, HNSW indexes and Postgres full-text search (`tsvector`, RRF fusion). No fake can
  reproduce ranking, so every adapter that touches SQL is tested against PostgreSQL 17 +
  pgvector started by testcontainers from the project's `db/Dockerfile`, never SQLite or mocks.
- **`create_app(settings=...)` is the seam for HTTP tests.** Settings are loaded in the
  lifespan, not at import, so a test builds a `Settings` object (factory in
  `tests/conftest.py`) and passes it in. `TestClient` used as a context manager runs the
  lifespan, which builds the real `Container` (engine, adapters). Without `with`, the lifespan
  does not run and `app.state.container` does not exist.
- **Configured libraries are used for real.** The SQLAlchemy engine (`pool_pre_ping`, asyncpg
  driver) and pydantic-settings validation are configuration contracts: mocking them would hide
  a wrong DSN scheme, a misspelled engine option (mypy cannot see `**kwargs`) or a missing env
  rule. Tests use real instances with test values.
- **LLMs are the only thing faked by design.** Provider calls cost money, are slow and are
  non-deterministic. The suite never touches the network: chat and embeddings use declared
  fakes behind the ports. langchain-core ships `GenericFakeChatModel`, `FakeListChatModel` and
  `DeterministicFakeEmbedding` for adapter-level tests; their vector size must match the
  pgvector column.
- **One event loop for the whole session.** pytest-asyncio 1.x runs with
  `asyncio_mode = "auto"` and both default loop scopes set to `session` in `pyproject.toml`.
  Session-scoped async engines and the tests that use them must share that loop, otherwise
  asyncpg raises "attached to a different loop".
- **Readiness is behavior.** `/health/ready` gates Compose and k8s; its 200/503 branches are
  tested at the HTTP layer against a real database, a database without the extension and an
  unreachable port.

## 2. Testing Criteria

**Worth testing**
- Settings with rules: required variables, empty-as-missing, provider-specific keys
  (`model_validator`), the `ConfigurationError` message that names each variable.
- Domain rules with branching: "not enough evidence" decision, citation filtering (drop chunk
  IDs that were not retrieved), document status transitions (indexing → ready/failed),
  supported-format checks.
- Use cases: orchestration branches (empty retrieval, provider failure, owner mismatch),
  owner and `Ready` filters always applied by the app.
- Postgres adapters: every query (filters, ranking, RRF, upserts, unique constraints, cascade on
  delete), mapping rows to domain types.
- LLM/embedding adapters: request mapping (model name from settings, prompt assembly, tool or
  structured output parsing) and provider error translation.
- Routes: status codes, validation wiring (one test per endpoint), error code mapping, 503 on
  dependencies, never leaking provider or SQL text.
- Document parsers: extraction of each supported format and rejection of the rest.

**NOT worth testing**
- FastAPI routing, Pydantic field presence or default values in DTOs without validators.
- That a use case "calls the repository" (wiring) without an observable result.
- The same branch repeated with different literal inputs.
- LangChain or SQLAlchemy internals (retry loops, pool mechanics).
- Exact LLM answer text: assert on structure, cited IDs and refusal, not prose.

## 5. Anti-patterns — Do NOT Do This

- ❌ **Unit test route functions by calling them directly** — routes are thin; test them
  through `TestClient` (see `artifacts/routes.md`).
- ❌ **Mock the database, use SQLite or an in-memory repository in integration tests** — the
  ranking and SQL contract only exist in real Postgres + pgvector
  (see `artifacts/postgres-adapters.md`).
- ❌ **Skip the integration test because the use case has a unit test with a fake
  repository** — the fake proves the use case, not the query (see `artifacts/use-cases.md`).
- ❌ **Mock the SQLAlchemy engine or pydantic-settings** — they are configured libraries; use
  real instances with test values (§1).
- ❌ **Call a real LLM or embedding API from any test** — use port fakes or langchain-core
  fakes (see `references/external-systems.md`).
- ❌ **Use `TestClient(app)` without `with`** — the lifespan does not run, so the container is
  missing (see `references/gotchas.md`).
- ❌ **Import fixtures or helpers from `conftest.py`** — fixtures are factories injected by
  pytest; shared helpers go in a regular module (see `references/file-conventions.md`).
- ❌ **Assert on LLM prose or snapshot answer text** — assert cited chunk IDs, refusal and
  status (§2).
- ❌ **Catch broad exceptions to make a test pass** — programming errors must surface as 500
  (see `artifacts/routes.md`).
- ❌ **Write mirror tests** — an assertion that copies the implementation's literal proves
  nothing (§2).

## 6. E2E Terminology Note

In this guide "HTTP tests" (what the fundamentals call E2E) means tests that drive the real
FastAPI stack through `TestClient`: request → routing → dependencies → response. Browser
end-to-end tests against the Docker Compose stack are Playwright tests, owned by the frontend
guide (`testing-guide-cwyd-frontend`).
